Scelte che vale la pena spiegare

Non solo cosa, ma perché — incluse le scelte scomode, documentate invece che nascoste.

Sicurezza multi-tenant esplicita

Ogni rotta che tocca una risorsa di un'azienda verifica requester.companyId === risorsa.companyId subito dopo l'autenticazione — è la difesa contro l'IDOR cross-tenant, applicata manualmente in ogni controller e documentata in CLAUDE.md come pattern obbligatorio.

Niente logica nei controller

I controller TSOA ricevono la request, chiamano il service, mappano il risultato sulla risposta HTTP. Qualunque validazione di dominio o accesso ai dati vive nei service, mai nel controller.

AI locale, non un'API cloud

L'assistente integrato invoca un modello Ollama in esecuzione sulla stessa rete, non un servizio esterno: coerente con il modello on-prem del prodotto, dati aziendali compresi quelli passati all'assistente non lasciano la rete locale.

Modello più piccolo scelto per affidabilità, non per risparmiare risorse

Il default è qwen2.5:7b, non un modello più grande. Test empirici ripetuti a parità di prompt e strumenti hanno mostrato che qwen2.5:14b dichiarava azioni riuscite senza aver mai chiamato il tool corrispondente (o dopo un suo fallimento), mentre il 7b ammetteva sempre l'errore o chiedeva conferma. Contro-intuitivo, ma verificato — vedi il commento sopra MODEL in assistantService.ts. Il modello resta comunque solo metà della difesa: il testo di conferma di ogni azione mutante è composto in codice dal risultato reale del tool (buildMutationConfirmation()), mai dal testo libero generato dal modello.

Modello di rete on-prem dichiarato

Hodum non è pensato per essere esposto direttamente su internet: l'accesso remoto passa da VPN aziendale. È un vincolo di design dichiarato nel README, non un dettaglio implicito da scoprire in produzione.

Un limite noto, documentato invece che nascosto

Il backend non ha uno script di lint dedicato: typescript-eslint non supporta ancora TypeScript 7, usato qui per tsc -b/tsoa:gen. Un workaround via override npm è stato tentato e si è rivelato inaffidabile — la scelta e il perché sono scritti in CLAUDE.md, non lasciati come un buco silenzioso.

Convenzioni di progetto

Applicate in ogni contributo, umano o assistito da AI.

📁

Componenti

src/app/components/<nome>/, con CSS co-locato e naming NomeComponent.

🗂️

Pagine

src/app/pages/<nome>/, registrate nell'array ROUTES centrale.

🧪

Test

Co-locati col codice, import espliciti da vitest: niente globals.

🗃️

Migration

File SQL numerati in backend/migrations/, applicate con npm run migrate:up.

Avvio in locale per sviluppo

  • 1 Frontend e backend hanno package.json separati: si installano e avviano indipendentemente.
  • 2 Il backend rigenera routes e spec TSOA a ogni avvio in watch mode, dai tipi dei controller.
  • 3 Serve un'istanza PostgreSQL raggiungibile e, per l'assistente, Ollama in esecuzione con il modello già scaricato.
  • 4 Prima di una pull request: npm run lint, npm test e npm run build su entrambe le cartelle.
# Frontend (root del repo)
npm install
npm run dev

# Backend
cd backend
npm install
cp .env.example .env
npm run migrate:up
npm run dev
